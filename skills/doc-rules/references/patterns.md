# Detection Patterns

## 1. AI-tone phrases

NG例と修正方針:

| NG | 理由 | 直し方 |
|----|------|--------|
| 「効率的に活用」「最適化」 | 意味が曖昧なまま良さそうに見せる | 具体的に何がどう良いか書く。書けないなら削る |
| 「構造化して蓄積」「体系的に管理」 | 大仰。実態は「ファイルに保存」程度 | 実態に合った平易な表現にする |
| 「シームレスに統合」「堅牢な」 | 製品紹介のマーケティング用語 | 削る。技術文書に形容詞はほぼ不要 |
| 「〜を提供する」「〜を実現する」 | 主語がツールで、自画自賛になる | 主語を人にするか、機能を端的に書く |
| 「プロジェクト横断的な学び」 | 抽象的で中身がない | 具体的に何を指すか書く |

## 2. Verbose structure

| NG | 直し方 |
|----|--------|
| 一文で済む内容を番号付きリストで4段階に分解 | 一文にまとめる |
| 同じことを言い換えて繰り返す | 一度だけ書く |
| 「〜することができます」「〜することが可能です」 | 「〜できる」 |
| 「〜を行う」「〜の実施」 | 動詞をそのまま使う（「テストを行う」→「テストする」） |
| 見出しの後に見出しを言い換えた導入文 | 導入文を削る。本題から始める |
| 1 つの文書に概要と詳細を全部入れて肥大化 | 概要だけ読みたい人に備え、詳細は別の文書へ分ける |

## 3. Self-evident explanations

| NG | 直し方 |
|----|--------|
| README に「これは〜のリポジトリです」 | タイトルで自明。削る |
| 「前提条件: 対象ツールがインストール済み」のためだけのセクション | セットアップ手順の中に一言添えれば十分 |
| 使い方が自明な機能の「基本的な使い方」セクション | 削る |
| 他ドキュメントへのリンクを文中に埋める | 飛び先が拾いにくい。独立した行にして目に付く形にする |

## 4. Dual-angle redundancy（二目線の重複）

同じことを裏表の 2 文で書くと、正確になるが情報過多になる。動作だけ書く。

| NG | 直し方 |
|----|--------|
| 「A が無いので B する」（B だけで足りる） | 「B する」 |
| 状態と対処を裏表で 2 文に分ける | 対処の動作だけ書く |
| エラー文の後の（）内で内部詳細を説明 | コード形式の短い英字文言にする（例: `file not found`） |

## 5. How-to writing（手順書の書き方）

何も考えず上から沿えば目的が達成できる形にする。文面や裏を読ませない。
直線的な手順は番号付きの節にし、必要事項を先頭に列挙する。実行部はコピペできる
1 ブロックにまとめ、操作だけを書く。なぜ（内部事情・仕組み）は削り、何をするかが
分かれば足りる。ただし容量・後始末・破壊的操作など、読者の行動を左右する注意は残す。

| NG | 直し方 |
|----|--------|
| 手順が地の文に散らばり、読まないと何を実行するか分からない | 実行するコマンドをコピペできる 1 ブロックに集める |
| 直線的な手順に番号がない | 節を番号付きにして順序を明示する |
| 見出しがアクションを指さず、説明だけの節を手順に置く | 見出しは読者が行う操作を名指す。説明だけなら前後の節に畳む |
| 前提を本文で説明する | 必要事項として先頭に箇条書きで並べる |
| 内部事情や仕組みを説明する | 操作だけ書く。なぜ（内部依存の都合など）は削る。要る操作が分かれば足りる |
| 行動を左右する注意まで削る | 容量・後始末・破壊的操作の警告は残す。削るのは仕組みの説明であって、操作を左右する注意ではない |
| どうしても外せない理由がある | 手順に混ぜず、別の節に分ける |
| 既定のある任意オプションをコマンド例に書く | 使うものだけ書く。既定任せでよいオプションは省く |
| 「〜なら」「合わなければ」など指す対象が曖昧な条件で始める | 何を指すか明示するか、条件を外して操作だけ書く |
| 確認手順に成功時の状態しか書かない | 失敗時に何が出るか（見分け方）も添える |
| 本当に複数環境が要る手順を地の文やコメントで分岐する | 環境ごとに見出しで分け、各ブロックを自己完結させる |
| 対象が 1 つに決まっているのに複数環境を分岐して書く | 使う環境だけ書く |
| 「要らないもの」を並べる | 要るものだけ書く |
| 読者の属性を名指しする | 名指ししない。誰が読むかは規定しない |
| 作業場所を指定する | どこでやるかは使い手の判断。規定しない |

## 6. Rule/reference docs（ルール・参照文書）

ルールやリファレンスは、それ単体で読んで意味が通る形にする。

| NG | 直し方 |
|----|--------|
| 特定プロジェクトの固有名・一回性の事例を例に使う | 汎用の例に置き換え、どの文脈でも読める形にする |
| 「既存に合わせる」等、外部の文脈に依存した指示 | 観点そのものを書き、単体で完結させる |
